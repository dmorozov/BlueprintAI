## Question

What are the concrete, source-verified recipes for fixing or at least *exposing* a dead session without replacing Viro? Deliver file-level steps for an Expo SDK 57 app, ordered by expected value, each with its unknowns-to-test:

1. **#1762 sensor workaround placement.** When exactly does Viro create/resume its ARCore session on Android (read `@reactvision/react-viro` 2.58.1 `android/react_viro` sources: `VRTARSceneNavigator`, `ViroViewARCore` lifecycle — view attach? `onHostResume`? first frame?). Where can an app register no-op `SensorEventListener`s on the uncalibrated gyro/accel *before* that point — a local Expo Module `OnCreate` / `OnActivityEntersForeground` hook, `MainApplication.onCreate` via a config-plugin mod, or JS-side just before mounting `ViroARScene`? How to add `HIGH_SAMPLING_RATE_SENSORS` (app.json `android.permissions` vs a `withAndroidManifest` mod — cite the v57 docs). Does Android 16 require anything else for that permission?
2. **Error surfacing.** Does Viro expose *any* ARCore session/camera failure to JS — `ViroARScene.onError`, `onTrackingUpdated` reasons, `ViroARSceneNavigator` props (`autofocus`, `worldAlignment`, `videoQuality`), native logs only? Is there a session-failed path at all in `react_viro` / `viro_bridge`? What is the smallest patch (patch-package on the Java/Kotlin side, which is source-shipped) that would surface an `ArStatus` to JS?
3. **ARCore client swap.** Mechanics and risk of replacing Viro's ARCore bits with 1.56. Verified so far (claims-verification, C4): `libviro_arcore.so` imports 150 public `Ar*` symbols, all exported with the same `VERS_1.0` node by the 1.56.0 stub, so the dynamic link works — **but** the 1.56 stub calls into 1.56's `classes.jar` (`SessionCreateJniHelper`, new `useProjectedApk()`), so the whole `arcore_client` AAR (Java + JNI + stub) must be replaced together and the renderer AAR's bundled 1.51 stub removed. Runtime behaviour is UNVERIFIED. Is it plausibly relevant to H1–H3 on Android 16, or a no-op?
4. **Camera-release guard.** How to verify from the app that the device camera is free before mounting (Camera2 `CameraManager.AvailabilityCallback` via a tiny local module?) versus a JS-side delay; how expo-camera releases on unmount (v57 docs / source).
5. **Delivery under CNG / EAS.** `android/` and `ios/` are gitignored and regenerated by `expo prebuild`, so any Viro patch or AAR swap needs a repeatable mechanism: `pnpm patch` for Gradle/Java text plus a postinstall `zip -d` on the AAR; a git fork of `@reactvision/react-viro` consumed as a git dependency with swapped AARs committed; or a config plugin that rewrites the `node_modules` AAR at prebuild. Compare them (reproducibility, EAS compatibility, upgrade cost).

Known virocore behaviours to account for (verified): `SessionNative` discards the `ArStatus` of `ArSession_create/resume/update/setCameraTextureName` (only `configure()` checks it); a failed resume is logged as "AR session resumed" and leaves the session paused; JS receives exactly one forced `onTrackingUpdated(UNAVAILABLE, NONE)` per mount and then only changes. Whether Viro draws the camera background before tracking is `Normal` is **contested** between two source readings — settle it from `renderFrame` / `renderWaitingForTracking` in the renderer.

Findings go to `docs/research/viro-quick-fix-recipes.md` on branch `research/viro-quick-fix-recipes` (link it here). Cite primary sources (Viro sources, ARCore issue thread, Expo v57 docs). Mark UNVERIFIED anything not confirmed from source.

## Answer

Report: `docs/research/viro-quick-fix-recipes.md` on branch `research/viro-quick-fix-recipes`. A skeptic pass reviewed it against primary sources.

**Recipe 0 — the headline finding, promoted to its own ticket ([00](00-mount-viro-scene-navigator.md)):** the app renders `<ViroARScene>` bare; only `VRTARSceneNavigator` constructs `ViroViewARCore`, so **no AR engine instance is ever created**. Independently verified in this repo (`grep`/`git log -S` find no `SceneNavigator` in `src/`, ever). A 2-minute device check (absence of `VRTARSceneNavigator: === onAttachedToWindow START ===` in logcat) confirms it. This displaces H1-H4 as the leading hypothesis.

**Recipe 1 — error surfacing: not achievable from JS or patch-package.** `ViroARScene.onError` is never wired (the app's `onError` handler is dead code); `StartupListenerARCore.onFailure` only `Log.e`s; `ArSession_create/resume/update` statuses are discarded in C++. The npm package ships **AARs only** (no Java/Kotlin/C++ sources), so patch-package cannot touch the Java side - surfacing an `ArStatus` needs a virocore rebuild (ticket 08). Quick substitute: a local Expo Module tailing `logcat --pid=<self>` (logd permits own-pid reads) and forwarding ARCore `E/native` / Viro `onRendererFailed` lines as failure reasons.

**Recipe 2 - #1762 sensor workaround: deterministic placement found.** Add `android.permission.HIGH_SAMPLING_RATE_SENSORS` via app.json `android.permissions`; hold `TYPE_GYROSCOPE_UNCALIBRATED` + `TYPE_ACCELEROMETER_UNCALIBRATED` at `SENSOR_DELAY_FASTEST` from a local module via `await holdSensors()` **before mounting the navigator** (Expo's `OnActivityEntersForeground` does not fire when a screen mounts while already resumed, so the JS await is the reliable hook), re-armed on foreground. New AOSP finding that raises the stakes: sensorservice returns **PERMISSION_DENIED** (not a silent clamp) for >200 Hz requests from **debuggable** packages lacking the permission - and this app only ever runs as a dev build. Android 16 needs nothing extra.

**Recipe 3 - camera guard:** `awaitBackCameraAvailable()` on `CameraManager.AvailabilityCallback` (initial state is delivered on registration). expo-camera releases the camera only on view destroy (`unbindAll`, asynchronous); ARCore may hold resources up to 10 s after pause. AOSP's camera service evicts the older same-process client ("most recent open wins"), so H3 rarely *fails* a session - it downgrades the hypothesis.

**Recipe 4 - ARCore client swap:** ELF-verified drop-in (all 150 `Ar*` symbols present in the 1.56 stub) but **a no-op for H1-H3**; mechanics and risks documented only. The 1.56 AAR raises `min_apk_version` and duplicates `libarcore_sdk_c.so` with the renderer AAR.

**Delivery under CNG:** `android/` is gitignored, so any patch needs `pnpm patch` + a postinstall AAR edit, a git fork of the package, or a config plugin that rewrites `node_modules` at prebuild - all documented; none needed if ticket 00 fixes it.
