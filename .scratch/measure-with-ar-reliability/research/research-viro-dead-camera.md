## 1. Upstream issues #499 and #513 (ReactVision/viro)

### #499 — "[Android 16] Camera texture never connects to ARCore session — background permanently black on Samsung Galaxy S24"
- https://github.com/ReactVision/viro/issues/499 — opened 2026-07-21 by `Banksy68`, **open**, no labels, no linked PR/commit/branch.
- Setup: `@reactvision/react-viro@2.57.4`, Expo SDK 55, RN 0.83.6, Galaxy S24, Android 16.
- Symptom (body): background black; `onTrackingUpdated` **fires immediately and permanently** with `state=1 (TRACKING_UNAVAILABLE)`, `reason=1 (TRACKING_REASON_NONE)`; 3D objects render on black; Play-Store AR apps work on the same phone.
- Comments (all): 2026-08-21 reporter asks for traction; 2026-08-24 maintainer `oliedis`: "We've been unable to reproduce this issue, if we're able to get some logcat outputs though we'll be able to better diagnose and resolve this issue." No root cause, no workaround, not fixed.
- Note: 2.57.4 (2026-07-09) already contained the `refreshCameraBackground` pause→resume workaround (commit `d6f5a99f`, same day, earlier), so that workaround did not prevent #499.

### #513 — "Camera background stays black (TRACKING_UNAVAILABLE persists) on Expo managed workflow — Samsung Galaxy A54"
- https://github.com/ReactVision/viro/issues/513 — opened 2026-08-07 by `cv-trx`, **open**.
- Setup: react-viro **2.43.6**, Expo 54, RN 0.81.5, EAS dev build, `newArchEnabled` both true/false → same result. Same symptom as #499 (state 1 / reason 1 forever; ArDoodle works on the same A54).
- Only comment: 2026-08-24 `oliedis`: "you're using a very out of date version… ViroReact is now on version 2.58.5 which relies on Expo 56 or 57. Are you able to test using a more up to date development setup and report back?" (No 2.58.5 exists on npm or GitHub as of 2026-09-14 — npm `latest` = 2.58.1; **UNVERIFIED** whether a 2.58.5 exists privately/Discord.)

### Difference from this app's symptom
Both upstream reports get `onTrackingUpdated(UNAVAILABLE, NONE)`. In this app the callback **never fires**. See §4 for why the renderer's code makes "never fires" the expected signature of a session whose `ArSession_resume()` failed or whose tracking never leaves `PAUSED`.

### Related issues (repo search: black/camera/Android 16/API 36/SurfaceTexture/onTrackingUpdated/16 KB/ARCore)
- #491 (closed 2026-07-09) 16 KB `libvrapi.so` RELRO crash on Android 15/16 → fixed in v2.57.3 by dropping OVR. #485 (closed) `libopenxr_loader.so`/`libc++_shared.so` 4 KB → fixed v2.57.0. #429, #400 (closed) earlier 16 KB reports.
- No issue mentions `SurfaceTexture`, `API 36`, or an ARCore version bump. Nothing else matches the black-camera symptom.
- Commit `d6f5a99f` (2026-07-09) "Temporary fix for black screen in a scene on android": in `VRTARSceneNavigator.StartupListenerARCore.onSuccess()` replay `arView.onActivityPaused(activity); arView.onActivityResumed(activity);` with the comment "First-mount ordering race in the renderer: on a cold AR mount the ARCore session can bind its camera texture before the GL thread creates that texture (onSurfaceCreated), so the passthrough stays black while 3D content still renders… Proper fix belongs in the renderer." **Removed** in v2.57.5 (PR #505, 2026-07-27): release notes say the replay blocked the main thread (~5 s ANR) and "The workaround was removed now that the renderer handles camera-texture binding natively; the black-passthrough issue it guarded against stays fixed." The shipped 2.58.1 `react_viro-release.aar` confirms `refreshCameraBackground` is absent (javap).

## 3. Google ARCore SDK support / deprecation policy

- `https://developers.google.com/ar/develop/deprecation-policy` → **HTTP 404**. The only policy page is https://developers.google.com/ar/distribute/deprecation-policy and it covers **only the Cloud Anchor API** ("make commercially reasonable efforts to continue to operate these services for one year after that announcement"; no commitment for pre-1.12). There is **no published general support window for old client SDKs**.
- Precedents of Google removing old-SDK behaviour: https://developers.google.com/ar/develop/c/ndk-camera-deprecation — "Apps compiled with ARCore SDK version 1.23.0 or later will not be affected"; older apps "might start to behave differently or crash when users update Google Play Services for AR" (Nov 2022). 32-bit-only app support removal (Aug 2020, https://developers.google.com/ar/64bit).
- The C API reserves `AR_UNAVAILABLE_SDK_TOO_OLD` = "The ARCore APK currently installed no longer supports the ARCore SDK that the application was built with." (returned by `ArSession_create`; https://developers.google.com/ar/reference/c/group/shared-types). Viro's `SessionNative` ctor calls `ArSession_create(...)` **without checking the status** (`android/viroar/src/main/cpp/arcore/ARCore_Native.cpp`), so such a failure would be silent — but there is no evidence it occurs: ARCore issue #1762 shows apps built with SDK 1.44/1.48/1.50/1.52 still creating sessions on APK 1.54.
- ARCore Android SDK release notes 1.44 → 1.56 (https://github.com/google-ar/arcore-android-sdk/releases): 1.44 (2024-06-21) bug fixes; 1.45 (2024-08-15) Flash Mode API; 1.46 (2024-10-10) `targetSdkVersion` → 35; 1.47, 1.49, 1.53 bug fixes; 1.48 (2025-02-27) HardwareBuffer playback fix; 1.50 (2025-07-11) `targetSdkVersion` → 36; 1.51 (2025-10-22) samples minSdk 23 / Vulkan sample; 1.52 (2025-12-12) "Verified this version of ARCore is compatible with Android 16 MR1"; 1.54 (2026-04-22) `ArCoreNativeInterop`; 1.56 (2026-09-04) `targetSdkVersion` → 37, `AcquireDepthImageMeters`. **No breaking changes, no SDK cut-offs, nothing about camera textures or Samsung.** (No 1.55 tag on GitHub, but Play Services for AR 1.55.261550593 shipped per ARCore issue #1779.)
- Conclusion for Q3: nothing indicates a 1.43/1.51 client is outside a support window in Sept 2026. Low-probability cause.

## 4. Android 16 / Samsung One UI 8 factors

### Android 16 platform changes
- All apps (https://developer.android.com/about/versions/16/behavior-changes-all): 16 KB page-size compat mode, JobScheduler quotas, ART updates, ordered-broadcast priority scope, intent-redirection hardening, accessibility announcement deprecation, predictive back on 3-button nav. **Nothing about Camera2, SurfaceTexture, OpenGL/EGL, or external OES textures.**
- Targeting 36 (https://developer.android.com/about/versions/16/behavior-changes-16): edge-to-edge mandatory, predictive back default (this app opts out via `enableOnBackInvokedCallback=false`), orientation/resizability ignored on ≥600 dp, BODY_SENSORS split, safer intents, MediaStore version, local-network permission. Again nothing camera/GL related.
- 16 KB (https://developer.android.com/guide/practices/page-sizes): Play requires 16 KB support for apps targeting API 35+ from 2027-02-01; Android 16 runs 4 KB-only apps in a backcompat mode with a warning. Not applicable: device page size is 4096 and all Viro/ARCore libs are 16 KB aligned. **Refuted as a cause.**
- Camera privacy toggle (https://developer.android.com/training/permissions/explaining-access): "When the user turns off camera access, your app receives a blank camera feed" (no error). Device currently has the toggle off (camera allowed) — refuted for the current state; re-check if it ever reproduces.

### Samsung + Android 16 + Google Play Services for AR ≥ 1.54 (the big one)
- **google-ar/arcore-android-sdk #1762** (open, label `bug`, 20 comments, last 2026-07-23): https://github.com/google-ar/arcore-android-sdk/issues/1762 — "FatalException from Session.resume() on Samsung SM-X520 / One UI 8.0 — regression after Play Services for AR auto-update to 1.54.x". Google's own unmodified `hello_ar_java` fails; native log `android_data_source.cc:1073 Failed to register sensor to queue 0` (`android_sensors.cc:139`). Reproduced by many on **Samsung Android 16 / One UI 8** devices: Tab S10 FE, S25 FE, A16 5G, S24 FE, A35, A56, A14, A53, S26+, A25 (fingerprint `a25x:16/BP2A.250605.031.A3` — same Android 16 platform build id as this S22 Ultra), S24+, Unreal/Depth-API samples ("Resume with error status -2"). Google (`lferrer`, 2026-05-06): "We have identified the source of the regression and are in the process of preparing a hotfix release." No later Google comment; reporters still failing on 1.54 in July. Google's non-repro list included a Galaxy S22 (`g0q`) but on **Android 14**. Whether 1.55/1.56 contains the hotfix is **UNVERIFIED** (1.56 notes are silent).
  - Community root-cause (comment 2026-04-27): Samsung HAL routes `EnableSensor` for uncalibrated gyro/accel through `queueBatch` unless those sensors are already streaming; ARCore's `standard_event_provider` can't handle that. Apps whose sensor stack keeps those sensors streaming are immune (explains intermittency).
  - **Workarounds reported to work**: (a) before creating the ARCore session, register a no-op `SensorEventListener` for `TYPE_GYROSCOPE_UNCALIBRATED` and `TYPE_ACCELEROMETER_UNCALIBRATED` at `SENSOR_DELAY_FASTEST` and declare `android.permission.HIGH_SAMPLING_RATE_SENSORS` (normal permission); one reporter (A56, Android 16) says the **permission alone** fixed it; (b) sideload Play Services for AR **1.53** (GitHub release APK) — "immediately fixes it… Re-installing 1.54 reproduces the failure again".
- **#1784** (2026-09-07, open): Galaxy A54, Android 16 / One UI 8.5, ARCore **1.56.262080393**: official Hello AR shows the camera but VIO never tracks (`FEATURE_DSP_CAM_IMU_DESYNC`, `VIO_OUTPUT_NOT_TRACKING`), survives factory reset; same APK works on an A14. **#1785** (2026-09-09) Tab S11 Android 16 camera-IMU desync; **#1761** (2026-04-12) "ARCore 1.53 breaks IMU tracking on Samsung Galaxy Z Fold 2 (Android 16)"; **#1769** (2026-06-19) native crashes in `libarcore_c.so` on A56 / Android 16.
- Samsung community threads report general camera breakage after One UI 8 patches (S23 Ultra Feb-2026 patch, A16) — secondary, not ARCore-specific.

### How Viro turns an ARCore failure into "black + no callback" (from virocore source)
- `ARCore_Native.cpp`: `SessionNative::resume()` is literally `ArSession_resume(_session);` — the `ArStatus` is discarded; same for `ArSession_update`, `ArSession_create`, `ArSession_setCameraTextureName`. `VROARSessionARCore::run()` then logs "AR session resumed" regardless.
- `VROSceneRendererARCore::renderFrame()`: `updateFrame()` → `arScene->setTrackingState(camera->getTrackingState(), reason, false)`; `VROARScene::setTrackingState` returns early unless state/reason **changed** from the initial `(Unavailable, None)` (`VROARScene.h:58-59`). `FrameNative::getTrackingState` maps `AR_TRACKING_STATE_PAUSED`/`STOPPED` → `NotTracking` → `VROARTrackingState::Unavailable`; `AR_TRACKING_FAILURE_REASON_BAD_STATE` → `None`.
- Therefore, if `ArSession_resume` fails (`AR_ERROR_FATAL` as in #1762, or `AR_ERROR_CAMERA_NOT_AVAILABLE`) the session stays paused, every `ArSession_update` returns `AR_ERROR_SESSION_PAUSED` ("An operation was attempted that requires the session be running, but the session was paused"), the frame's camera stays `PAUSED`, the mapped state equals the initial state, and **`onTrackingUpdated` is never emitted** — while nothing crashes and Viro's own logs look healthy. The same holds if tracking runs but never leaves `PAUSED` with `BAD_STATE`.
- `renderWaitingForTracking()` ("Render black while waiting for the AR session to initialize") is used whenever tracking != `Normal`; the camera passthrough is only drawn in `renderWithTracking`. So a Viro scene is black in **any** not-yet-tracking state, whereas Google's HelloAR shows the camera feed even when VIO fails (#1784). "Other AR apps show the camera" does not by itself exonerate ARCore.

### App-side camera ownership (from `src/screens/ar-capture-screen.tsx`, `photo-assist-screen.tsx`, `capture-screen.tsx`)
- The AR screen swaps between a `ViroARScene` phase and an `expo-camera` `CameraView` "photo" phase (comment: "Set when the preview fails to start (e.g. ARCore still releasing the camera)"); two other screens mount `CameraView` (unmounted on blur via `useFocusEffect`). ARCore doc: after `ArSession_pause` "ARCore might continue consuming substantial computing resources for up to 10 seconds". A camera still held when `ArSession_resume` runs yields `AR_ERROR_CAMERA_NOT_AVAILABLE` ("The Android camera has been reallocated to a higher priority application or is otherwise unavailable") — which Viro swallows. **UNVERIFIED** on this device; Android's CameraService normally lets a same-priority foreground client evict the older one, which argues against this being deterministic.
- Logcat also shows Samsung's `com.samsung.android.smartface` (PID 19083) opening/closing **camera 1** periodically — observed, not implicated.

## 5. Local patch feasibility

- `libviro_arcore.so` links `libarcore_sdk_c.so` dynamically (DT_NEEDED) and references only public `Ar*` C-API symbols (328 exported by the stub). The stub is a thin loader ("ARCore SDK: dynamite number_of_symbols_loaded", "failed to load symbols") that pulls the implementation from the installed Play Services for AR APK. Google's C API is additive, so dropping in the **stock 1.56.0 `libarcore_sdk_c.so`** (68,072 B, 16 KB aligned, superset of 1.51 exports; from https://dl.google.com/dl/android/maven2/com/google/ar/core/1.56.0/core-1.56.0.aar) should load without rebuilding `libviro_arcore.so` (**UNVERIFIED at runtime**).
- Cleanest form: replace Gradle `implementation project(':arcore_client')` with `implementation 'com.google.ar:core:1.56.0'` (matched Java + JNI + C), and remove the stale copy inside `viro_renderer-release.aar` (`zip -d viro_renderer-release.aar 'jni/*/libarcore_sdk_c.so'` in a postinstall step — `patch-package` cannot diff binary aars). The stock 1.56 manifest bumps `minSdkVersion` to 24 and `targetSdkVersion` to 37 (manifest merging; app already sets targetSdk 36 explicitly).
- **What the swap would and would not do**: it removes the Java/JNI-vs-C version skew and any "SDK too old" doubt; it does **not** fix the discarded `ArSession_resume` status, nor an ARCore-service/Samsung-HAL regression. Fixing Viro's error handling requires rebuilding `libviro_arcore.so`/`libviro_renderer.so` from virocore (Gradle + CMake + NDK 27.1; MIT; feasible but undocumented) and repacking the aar.
- The #1762 workaround needs **no Viro change**: add `<uses-permission android:name="android.permission.HIGH_SAMPLING_RATE_SENSORS"/>` and register the two uncalibrated sensor listeners (Kotlin, e.g. in `MainActivity` or a tiny native module invoked before the AR screen mounts), unregistering on pause.

## Does an upstream fix exist?

- **Viro**: No. Latest published 2.58.1; `release/2.58.2` and `develop` contain no Android camera/ARCore changes; maintainers "unable to reproduce" #499 (2026-08-24) and asked #513 to upgrade; the only related change was a workaround added 2026-07-09 and removed 2026-07-27. `arcore_client` is still `core-1.43.0.aar` on `main`; the renderer's C stub is 1.51. - **Google ARCore**: #1762 acknowledged (2026-05-06, "hotfix release" promised) but still open with failures reported through July on 1.54; no release note in 1.55/1.56 mentions it. ## Testable pre-requisites (concrete experiments on the connected SM-S908U)

1. **Capture a failing mount with ARCore's own logs** (the decisive test for H1/H2/H3): `adb logcat -c; adb logcat -v time > ar-fail.log`, open "Measure with AR", wait 20 s. Grep for: `ARCoreError`, `Failed to register sensor to queue`, `android_sensors.cc`, `session.cc:1476` (→ H1); `FEATURE_DSP_CAM_IMU_DESYNC`, `VIO_OUTPUT_NOT_TRACKING`, `kNotTracking` (→ H2); `CameraService: connect call`/`ERROR_CAMERA_IN_USE`/`EBUSY` for `com.anonymous.blueprintai` (→ H3); `ARCore Version: SDK build name: 1.51`; Viro lines `AR session resumed`, `ViroARCore: Selected camera config`, `AR camera texture`, `VRTARSceneNavigator: === onAttachedToWindow`, and any `onRendererFailed` (→ H4). Because Viro swallows statuses, ARCore's `E/native` lines are the only place the failure is visible.
2. **Control with Google's sample**: build `samples/hello_ar_kotlin` from google-ar/arcore-android-sdk (SDK 1.56) and run it on this phone. `Session.resume()` throwing `FatalException` → H1 confirmed (device/ARCore level, not Viro). Camera visible but no planes + desync logs → H2. Works fine → Viro-specific (H3/H4/H5).
3. **Apply the #1762 workaround app-side** (no Viro change): add `HIGH_SAMPLING_RATE_SENSORS` to the manifest and register no-op listeners for `TYPE_GYROSCOPE_UNCALIBRATED` and `TYPE_ACCELEROMETER_UNCALIBRATED` at `SENSOR_DELAY_FASTEST` before the AR screen mounts (unregister on pause). If the black screen stops reproducing → H1 confirmed and mitigated.
4. **Sideload Play Services for AR 1.53** (official GitHub release APK; disable auto-update temporarily). Viro works on 1.53 and fails again on 1.56 → H1. (Reporters used exactly this bisect.)
5. **Camera ownership while black**: `adb shell dumpsys media.camera` to see which client holds camera `0`; reproduce from a cold launch straight into the AR screen (never touching a `CameraView`), and separately right after the photo-assist screen. Difference → H3; also add a ~1.5 s delay between unmounting a `CameraView` and mounting `ViroARScene` as a probe.
6. **Correlate with the ARCore APK update**: the APK was updated **2026-08-29**; if "sometimes worked" was only before that date (check the user's memory / Play Store update history) → H1/H2 (service-side regression). ARCore 1.56 rolled out ~2026-09-04.
7. **GL/loop sanity** (H4): in the failing log, confirm `VRTARSceneNavigator: === onAttachedToWindow END (normal)` and Viro's surface/`AR session resumed` lines exist; if none, the GL surface never came up (interop problem) rather than ARCore.
8. **Version-skew probe** (H6, low priority): swap `:arcore_client` for `com.google.ar:core:1.56.0` and strip the renderer's 1.51 `libarcore_sdk_c.so`; verify `ArCoreApk` still reports `SUPPORTED_INSTALLED` and whether behaviour changes. Expected: no change.
